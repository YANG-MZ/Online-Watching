## 1. 项目概述

### 1.1 项目目标

开发一个基于 Web 的多人在线同步观影应用。用户创建观影房间后,通过邀请链接让其他用户加入。房主上传本地视频,所有成员通过浏览器访问同一视频;房主执行播放、暂停、拖动进度等操作时,由服务端将播放状态实时同步给所有成员,实现多人共同观看同一视频的体验。

**核心目标:**

1. 支持多人同时进入同一个观影房间。
2. 支持房主上传视频,所有成员均可观看。
3. 支持播放、暂停、进度跳转、倍速等操作实时同步。
4. 支持新成员中途加入,以及断线后的自动重连与状态恢复。
5. 个人音量、静音等观看偏好完全独立,不影响其他成员。

### 1.2 核心原则

**全局播放行为同步,个人观看偏好独立。**

## 2. 部署形态与容量约束

- **部署形态**:单实例部署,**优先部署到本地笔记本电脑**,面向局域网/熟人小圈子分享邀请链接的场景;后续可原样迁移至服务器部署。
- **硬性容量上限**(超出即拒绝,均可在配置文件中修改):
  - 最大房间数:**5 个**(超出时拒绝创建房间);
  - 每房间最大成员数:**10 人**(满员时拒绝加入);
  - 参考视频码率:≤ 20 Mbps。
- **带宽说明**:本方案为各成员独立从服务器拉流,带宽需求 ≈ Σ(各房间在线人数 × 码率)。理论上限 5 房 × 10 人 × 20 Mbps = 1 Gbps,远超笔记本网卡(尤其 Wi-Fi)能力;实际同时观看人数受笔记本网络环境限制,多人同时观看建议使用有线网络。
- **笔记本部署特性**:笔记本休眠/关机即服务中断;客户端自动重连机制(见 3.7)在服务恢复后自动恢复观看,无须人工干预。

## 3. 功能需求

### 3.1 房间管理

#### 3.1.1 创建房间

- 用户输入昵称后点击创建房间,系统生成房间 ID(不可猜测的短随机码)和邀请链接,创建者自动成为房主。
- 当前房间数达到配置上限(默认 5 个,见第 2 节)时,拒绝创建并给出明确提示。

#### 3.1.2 加入房间

- 支持通过房间 ID 或邀请链接加入。
- 加入时输入昵称,无需注册登录。
- 房间满员(达到配置上限,默认每房 10 人)时,拒绝加入并给出明确提示。
- 加入动作(输入昵称 + 点击加入)构成一次用户手势,用于满足浏览器自动播放策略要求(见 7.3)。

#### 3.1.3 成员列表与在线判定

- 实时展示当前**在线**成员及其昵称。
- 在线判定依赖 WebSocket 心跳(见 3.6.2):
  - 成员主动点击退出 → 立即移出成员列表;
  - 成员掉线 → 心跳超时(90 秒无消息)后移出成员列表。
- 昵称允许重复,成员以服务端签发的 `user_id` 区分(见 3.2.1)。

#### 3.1.4 离开与退出

- 成员可主动退出房间;关闭标签页/断网视为掉线,按心跳超时移出。

#### 3.1.5 房主移交规则

- **仅当房主主动退出房间时**,房主身份立即移交给**当前房间内加入时间最早**的其他成员(若房内已无其他成员,则不发生移交)。
- **房主掉线不移交**:房主身份保留,等待其重连恢复;期间房间播放状态由服务端继续维护,其他成员正常观看。
- 房主主动退出后再次进入房间,身份为普通成员。
- 移交发生时,服务端广播房主变更事件,全体成员更新界面显示。

#### 3.1.6 解散房间(新增功能)

- 房主可主动解散房间,操作需二次确认。
- 解散后:全体成员收到"房间已解散"通知并被移出,房间状态与视频文件**立即**清理。

#### 3.1.7 房间生命周期

```
成员移除:主动退出 → 立即移除;掉线 → 心跳超时(90s)后移除
房主移交:仅房主主动退出时,移交给加入最早的在房成员
房间过期:在线成员列表变为空后 10 分钟(可配置),房间与视频文件被清理
房间解散:房主主动解散 → 全员移出、文件立即清理
兜底:    服务重启 → 房间失效(见 4.5);清理任务依据 SQLite 元数据删除残留文件
```

- 只要房间一直有成员在线,房间无绝对时长上限。
- 房间内显示当前视频及播放状态。

### 3.2 身份与权限

#### 3.2.1 身份凭证机制

- 无注册登录。用户创建或加入房间时,服务端签发 `user_id` 与随机 `session_token`,客户端存入 localStorage。
- 后续所有 HTTP 请求与 WebSocket 消息携带该 token;断线重连、刷新页面后凭 token 恢复身份,成员列表不出现重复。
- 房主标记由服务端房间成员状态维护(可随移交变更),不固化在 token 内。
- 清除浏览器缓存即失去身份凭证(含房主身份),V1 接受此限制。

#### 3.2.2 权限控制

- 以下操作仅房主可用,服务端必须校验房主权限,不能仅依靠前端隐藏按钮:
  - 上传/替换视频;
  - 播放、暂停、进度跳转、倍速调整;
  - 解散房间。
- 普通成员直接调用房主控制接口必须被服务端拒绝(403)。
- V1 接受"持有邀请链接即可加入房间",房间不设密码。

---

### 3.3 视频上传与管理

- 仅房主拥有上传权限。
- 支持上传本地视频文件,**仅支持 MP4 容器**(视频 H.264、音频 AAC);V1 仅校验 `.mp4` 扩展名,不引入 ffprobe/ffmpeg 做深度校验(见 7.1)。
- 上传方式:整体流式上传,**不做分片上传与断点续传**;默认大小上限 **4 GB**(可配置),超限给予明确错误提示。
- 上传过程中向房主显示上传进度;上传失败提供明确错误提示;上传中断产生的临时文件纳入过期清理。
- 上传至服务端本地文件系统,文件以 **UUID 重命名存储**(URL 不可猜测,作为最低限度访问控制);元数据(文件名、大小、UUID、所属房间)记录于 SQLite。
- 上传完成后通过 WebSocket 广播"视频就绪"事件,全体成员加载播放器。
- 房间同一时刻仅一部视频;**房主可重新上传替换**:旧文件删除、播放进度归零、状态版本号递增、广播"视频变更"事件,成员播放器自动重新加载新视频。
- 视频访问支持 HTTP Range 请求,以支持拖动进度条与分段读取。

---

### 3.4 播放与同步

#### 3.4.1 权威状态模型

- **服务端是房间播放状态的唯一权威来源**,维护:
  - `state`:playing / paused;
  - `position`:最近一次更新时刻的播放位置;
  - `rate`:播放倍速;
  - `updated_at`:服务端时间戳;
  - `version`:状态版本号(单调递增)。
- 客户端推算当前播放位置:`position + (now - updated_at) × rate`(仅 playing 状态累加)。
- 客户端不能自行决定全局播放状态;收到版本号低于当前已知版本的事件直接丢弃,防止过期事件。
- 时钟偏差处理:以消息内服务端时间戳为准,必要时按 RTT 的一半补偿单向延迟,V1 不做更精确的时钟同步。

#### 3.4.2 同步的操作(仅房主触发)

| 操作 | 同步行为 |
| --- | --- |
| 播放 | 全员同步开始播放(以服务端推算位置为准) |
| 暂停 | 全员同步暂停在对应位置 |
| 进度跳转 | 拖动**结束(drag end)**时同步跳转,拖动过程不同步,避免事件风暴 |
| 倍速调整 | 全员同步调整播放速度 |

- 暂停状态下房主拖动进度条同样同步生效。

#### 3.4.3 偏差校准

- 客户端定期(如每 5~10 秒)按权威状态校准本地播放时间。
- 小偏差:渐进式校准(微调播放速率或短时 seek 抹平),不打断观看;
- 大偏差:直接 seek 跳转;
- 具体阈值在实现阶段确定,稳态偏差目标见 4.1。

#### 3.4.4 播放结束

- 视频自然播完(ended)**不广播全局事件**,各端自然结束;房主随后可再次播放或拖回进度。

---

### 3.5 个人播放偏好(不参与同步)

以下配置完全独立于房间全局状态,每个用户自行调整,**不发送给服务端**:

- **音量**:独立调整;
- **静音**:独立开关;
- **全屏**:独立进出。

偏好保存于 localStorage,刷新页面后保留。

示例:房间内 A 音量 80%、B 音量 30%、C 静音,互不影响;A 点击暂停则三人同时暂停,且个人音量设置不变。

---

### 3.6 实时通信

#### 3.6.1 通道与事件

- 使用 WebSocket 传输控制事件与房间状态,**不传输视频数据本身**(视频走 HTTP Range 拉流)。
- 事件清单:

| 事件 | 方向 |
| --- | --- |
| 成员加入 / 离开通知 | 服务端 → 全体 |
| 房主变更(移交/解散) | 服务端 → 全体 |
| 播放 / 暂停 / 进度跳转 / 倍速变更 | 房主 → 服务端 → 全体 |
| 视频就绪 / 视频变更(替换) | 服务端 → 全体 |
| 房间状态更新(含版本号) | 服务端 → 全体 |

#### 3.6.2 心跳

- 客户端每 30 秒发送 ping,服务端 90 秒未收到任何消息则判定连接死亡并移出成员列表。
- 心跳是在线判定、成员列表准确性、房主掉线判定的基础。

---

### 3.7 中途加入与异常恢复

- 新成员加入时,服务端返回**当前完整房间状态快照**(视频信息 + 播放状态 + 成员列表),而非补发历史事件。
- 新成员据此加载视频并定位到按权威状态推算的当前播放位置,无须从头观看。
- 断线后客户端自动指数退避重连 WebSocket;重连成功后携带 `session_token` 恢复身份,并**重新拉取全量状态快照**,不依赖断线期间遗漏的事件。
- 成员自身缓冲慢或网络差,仅影响其个人体验(由校准机制追赶),不得导致其他成员暂停。
- 房主掉线:保留房主身份与房间状态,不移交(见 3.1.5)。

## 4. 非功能需求

### 4.1 性能指标

- 正常网络下,房主操作到其他成员端生效 **≤ 1 秒**。
- 稳态播放时,各成员间播放位置偏差目标 **≤ 0.5 秒**。

### 4.2 容量与带宽

见第 2 节部署形态与容量约束。

### 4.3 安全

- 房主控制接口、上传接口、解散接口:服务端校验 `session_token` 与房主角色,拒绝越权(403)。
- 视频文件以 UUID 命名,URL 不可猜测;V1 接受"持有视频 URL 即可访问",不做逐请求鉴权。
- 房间 ID、`session_token`、文件 UUID 均使用密码学随机生成,不可预测。

### 4.4 兼容性

- 优先适配桌面端 Chrome 与 Edge;手机端专项适配列入后续版本规划(见 6.3),V1 不保证手机浏览器体验。

### 4.5 可靠性与运维

- **服务重启**:房间状态存于内存,重启后所有房间失效;客户端重连会收到"房间不存在"。已上传文件由清理任务依据 SQLite 元数据删除。此为 V1 接受的行为。
- **清理任务**:后台周期扫描,处理:全员离开超时的房间(见 3.1.7)、解散房间残留、上传中断的临时文件。
- 文件大小上限、房间过期时长等参数可配置。

## 5. 技术选型

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 前端 | Vue 3 + TypeScript | 房间页、播放器、成员列表、上传界面 |
| 播放 | HTML5 Video | 配合 HTTP Range 分段拉流 |
| 实时通道 | WebSocket | 仅控制事件与状态,不传视频 |
| 后端 | Python + FastAPI | HTTP API + 原生 WebSocket |
| 数据库 | **SQLite** | 房间/用户/视频元数据,供清理任务追溯 |
| 视频存储 | 服务端本地文件系统 | UUID 命名,与元数据分开管理 |
| 部署 | 单实例,优先部署到本地笔记本电脑 | 房间在线状态暂存内存,后续可迁移至服务器 |

- HTTP API 承担:房间创建、加入、退出、解散、视频上传、视频文件访问(Range)。
- 架构取舍说明:各成员独立从服务器拉流 + 仅同步控制信号,复杂度远低于 WebRTC 推流,V1 明确不做 P2P 传输。

## 6. 范围边界(V1.0)

### 6.1 必须实现

- 房间创建、加入、退出、解散。
- 容量上限控制(最大房间数、每房最大人数,均可配置)。
- 昵称与在线成员列表。
- 房主凭证、移交与掉线保留规则。
- 房主上传视频(含替换)。
- 多人访问同一视频。
- 播放、暂停、进度跳转、倍速同步。
- 独立音量、静音、全屏设置(localStorage 持久化)。
- WebSocket 实时通信与心跳。
- 中途加入、断线重连与状态恢复。
- 服务端权限校验与异常处理。
- 视频文件过期清理。

### 6.2 暂不实现

- 用户注册与登录系统。
- 多视频播放列表。
- 在线视频网站解析。
- 视频转码与多清晰度。
- 字幕上传与管理。
- 实时文字聊天与表情互动。
- 语音聊天与视频通话。
- WebRTC / P2P 视频传输。
- 多服务器集群部署。
- 手机端专项适配(V1 不做,已列入 6.3 后续规划)。
- 分片上传与断点续传。

### 6.3 后续版本规划(V1 之后)

- **手机端专项适配**:针对手机浏览器进行布局与交互优化,包括触屏手势控制(拖动进度条)、播放器交互适配、Wi-Fi/蜂窝网络切换场景的重连处理等。

## 7. 已知限制与风险

| # | 限制/风险 | 说明与缓解 |
| --- | --- | --- |
| 7.1 | 格式校验仅看扩展名 | 非 H.264/AAC 编码的 MP4 可能无法播放,V1 记为已知限制;将来可引入 ffprobe 深度校验 |
| 7.2 | moov atom 在文件尾的 MP4 加载慢 | 浏览器需先 Range 到文件尾获取元数据,V1 不做 faststart 处理,记为已知限制 |
| 7.3 | 浏览器 autoplay 策略 | 成员"输入昵称 + 点击加入"的用户手势通常可解除自动播放限制;若仍被拦截,前端提示用户点击一次页面 |
| 7.4 | 清除浏览器缓存丢失房主身份 | 无登录体系的固有限制,V1 接受;极端情况下房间等全员离开后过期清理 |
| 7.5 | 房主掉线期间房间无控制者 | 按规则不移交,播放继续;若房主不归且全员离开,10 分钟后房间过期 |
| 7.6 | 服务器上行带宽为规模瓶颈 | 见 2 节容量约束,部署时评估 |
| 7.7 | 上传大文件失败需整体重传 | V1 无断点续传,弱网下大文件上传体验有限,记为已知限制 |

## 8. 验收标准

### 8.1 功能验收

1. 两个及以上浏览器能同时进入同一房间。
2. 房主上传的视频能被所有成员正常播放(支持拖动进度条,即 HTTP Range 生效)。
3. 房主播放/暂停,其他成员同步响应。
4. 房主拖动进度条(松手后),其他成员跳转到对应进度。
5. 房主调整倍速,其他成员同步调整。
6. 不同成员音量/静音状态互不影响,且刷新页面后保留。
7. 新成员中途加入后能进入当前观影进度。
8. 成员断网恢复后能自动重连并获取正确房间状态,成员列表不出现重复。
9. 普通成员直接调用房主控制接口被服务端拒绝(403)。
10. 房间全员离开 10 分钟后,对应视频文件被清理。
11. 上传非 `.mp4` 文件或超过大小上限的文件被明确拒绝。
12. 房主重新上传替换视频后,成员播放器自动加载新视频,播放进度归零。
13. 房主主动退出后,房主身份移交给加入最早的在房成员,新房主可正常控制播放。
14. 房主掉线(心跳超时)期间房主身份不移交;房主重连后恢复控制权。
15. 房主解散房间后,全体成员收到通知并被移出,视频文件立即清理。
16. 房间数达到配置上限后,新建房间被拒绝并有明确提示;房间满员后,新成员加入被拒绝并有明确提示。
17. 修改配置文件中的容量上限值并重启服务后,新上限生效。

### 8.2 性能验收

1. 正常网络下,房主操作到其他成员端生效 ≤ 1 秒。
2. 稳态播放时,各成员间播放位置偏差 ≤ 0.5 秒。

## 附录 A:典型使用示例

**场景一:创建房间并开始观影**

1. A 输入昵称 `Alice` 创建房间,获得房间 ID 与邀请链接。
2. B、C 通过邀请链接加入。
3. 房主 A 上传 MP4 视频,上传完成后 B、C 加载播放器。
4. A 点击播放,三人同步开始观看。

**场景二:播放控制**

1. A 在第 120 秒暂停,服务端更新状态并广播,B、C 同步暂停。

**场景三:个人偏好独立**

**场景四:中途加入**

1. A、B 观看到第 500 秒,C 加入。
2. 服务端返回完整状态快照,C 定位到当前应播位置继续观看。

**场景五:房主移交**

1. 房主 A 主动退出,房主身份移交给最早加入的 B。
2. B 获得播放控制与上传权限,A 再次进入房间时为普通成员。
